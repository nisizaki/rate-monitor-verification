# 接続部分：許可、送信、モニター

`Permit_Operational.thy` は、共有トークンバケットの許可取得と送信を別々のイベントとして記述する。時刻の経過、許可の発行、送信、取消しがあり、発行済み ID は再利用しない。送信は未使用の許可に対してのみ可能で、許可時刻から D 以内という制約を遷移の前提としている。取消した許可を再利用することはできない。

`permit_run_valid` は、有効な初期状態からの実行で、許可集合の有限性、発行済み集合への包含、保留と送信済みの非交差、送信時刻の許可時刻以降かつ D 以内という性質が保存されることを示す。許可から D 以内に必ず送信するという進行性は示していない。`permit_monitor_matches` は、許可を Send に、送信と取消しを Other に写したイベント列に対して、モニターがバケット残量と一致することを示す。

`Permit_Bridge.thy` の `concurrent_middle_bound` は、並行モデルの有限実行の任意の連続部分列にバケットの上限を適用する。`concurrent_operational_fetch_bound` は、並行モデルの実行、許可・送信モデルの実行と初期不変条件、次の区間対応を仮定し、任意の半開区間 [a,b) の送信回数が `B + r * ((b-a)+D)` 以下であることを証明する。

ここで `window_correspondence` は、各許可時刻区間に対応する連続部分列が存在し、その中の許可数が区間内の許可 ID 数と等しく、部分列の経過時間が区間幅以下である、という仮定である。この対応はまだ遷移系から導出されていない。特に並行モデルの `SendRequest` を許可発行として解釈する必要があり、2 つの実行が同じ実際の実行に対応することも定理では保証していない。既存の再試行モデルとの精密化関係、TypeScript の実装・計装との対応、実環境での D の保証は未証明である。

次の課題は、時刻付きの共通イベント列から区間対応を導き、両モデルと再試行・監視を同じ実行に結び付けること、その後に実装の対応条件と計測方法を定めることである。D はサービス仕様から得た値ではなく、モデル上のパラメーター・送信時の制約である。
