# Evaluation protocol and current status

## Status

Three successful Slack/DeepL smoke tests have been run, one per mode; they are not a controlled comparison. See deeplbot3x/README.md for details. The preliminary controlled local measurement is an optional, sequential, single-process local Deno mock benchmark (`experiments/local_benchmark.ts`). It is not a Slack Function benchmark and is not evidence of production latency, cross-function sharing, observation completeness, or compliance with DeepL policy.

Run it from the repository root with `deno run --no-config experiments/local_benchmark.ts > result.json`. It requests no network, environment, file or subprocess permissions. It uses the pinned DeepL client fixture, a synthetic response, an in-memory event list, and a handwritten monitor with capacity 1800 and refill rate zero. After 300 warmups, it measures 1,500 sequential calls per mode and rotates the mode order each round. Timings cover the local translation call and harness setup; they do not isolate the monitor alone. The timer resolution has not been independently characterized.

One preliminary run is recorded in `results/local-mock-2026-10-28.json`, including per-call samples. On Deno 2.9.7, Linux aarch64, p50 values were approximately 0.0029 ms (baseline), 0.0035 ms (record), and 0.0036 ms (monitor); p95 values were approximately 0.0044, 0.0051, and 0.0053 ms, respectively. Each mode had 1,500 measured calls, and the two observed modes each recorded 1,500 events; this count is within the controlled harness, not independent proof of complete observation in Slack. These small differences are from a single unreplicated run and must not be interpreted as a reliable overhead estimate.

## Research questions and measurement

1. **Functionality:** compare return class, number of client-side `fetchFn` calls, and success/failure path across baseline, observation-only, and observation plus monitor modes. The same controlled test inputs and fake responses must be used, including an intentional 429, 456, malformed response, and client-side timeout.
2. **Observation coverage:** on an instrumented test build, give each expected invocation a unique opaque test ID and compare an independently collected invocation ledger with recorded `InvokeFetch` IDs, including duplicates, missing entries, and ordering. Independent observation must not be inferred from the same log stream. If such a ledger is unavailable, report coverage as unknown rather than 100%.
3. **Overhead:** measure event-recording/monitor processing time around the instrumentation with a monotonic clock and measure complete Function elapsed time separately. Report sample count, p50, p95, p99, failures, missing data, and raw data provenance. Compare matched workloads and alternate or randomize mode order; repeat over multiple sessions and describe variability. Clock resolution and measurement overhead must be measured or stated.
4. **Policy decision:** compare the monitor output against the recorded event stream under explicit B, r, initial balance, time unit, ordering and rounding rules. Treat missing, duplicate, unordered or incomplete observations as inconclusive; the current two-valued monitor does not implement a completeness verdict.
5. **Deadline and delay:** if a permit-based implementation exists, record permit grant and fetch times on the same monotonic clock, identify permit IDs and canceled/expired permits, and report observed delay distribution and deadline misses. A measured maximum does not prove the assumed bound D.

## Environment and deployment requirements

Record the code commit and build, Deno/Slack CLI versions, region/runtime, execution type (deployed Function or `slack run`), concurrency, configuration and sample sizes. Use a designated test workspace and channel, synthetic texts, test credentials provided through the existing secret mechanism, and a controlled mock endpoint where possible. Never save credentials, authorization headers, message text, or translated text in trace logs. Do not redirect real credentials to an untrusted mock. Establish that the fixture and permissions are isolated before triggering test messages. Actual Slack writes and any deployment must be explicitly authorized for the identified destination; a test is not performed merely because the CLI is logged in.

The existing client has no shared limiter, retries, grant events, or runtime observer. An experimental build has been prepared for comparison in Slack; a controlled live comparison remains to be performed. Its deployment and any effect on existing workflows must be reviewed. A single-process monitor does not establish shared monitoring across independently running Slack Functions; clock origins and aggregation/order across instances are separate open issues. A 429 or 456 generated by a mock is a test stimulus, not evidence of a DeepL rate-limit rule.

## Reproducibility and interpretation

Store exact run configuration, start/end time, source commit, test versions, exclusions, deviations, raw anonymous measurements and aggregation script. Record both successful and failed cases. Define expected operation counts before running. Avoid baseline drift by rotating or randomizing modes and reporting unpaired effects where pairing is unavailable. No significance or production overhead claim follows from the local preliminary run.

The proof in `Permit_Bridge.thy` assumes `window_correspondence`; this experiment cannot turn the assumption into a theorem. Likewise test passes do not prove TypeScript refinement, observation completeness, or timing preservation for all executions.


## Repaired experimental candidate (local preparation only)

The current DeepLbot3x patch adds shared measurements to baseline as well as record and monitor. UUID creation, timing, Unicode codepoint counting, synchronous exception protection and common log emission all contribute baseline overhead. Compare modes with that definition; no uninstrumented-control claim is justified. The new candidate has not been deployed or used for live smoke trials.

Observation faults must not suppress or retry translation/fetch, replace successful values or original rejection values, or fabricate measured zeroes. Local fault regressions cover synchronous faults; process termination, OOM, asynchronous sinks and delivery loss remain limitations. See deeplbot3x/repair-report.md.

Before a separately authorized one-shot trial per mode, freeze the patch/source identity, runtime/configuration versions, synthetic input size, mode and non-secret trial UUID. Keep those trials separate from proposed full repetitions. Full repetitions require a prespecified budget, warmup policy, randomized/rotated mode order, matched workloads, concurrency and cold/warm policy, and failure/missingness rules.

Completeness remains unknown without an independent denominator. Planned posts and sequence numbers cannot detect all entirely missing invocations or the last lost event. Report sample counts and missing values alongside timing percentiles. Submitted Unicode codepoints after placeholder processing are not API-reported billed characters. A partial observed character sum is not total consumption; zero valid measurements produce null. Usage/quota is independently checked through the official account interface.

Deployment is a separate decision: inspect the complete app manifest/workflow impact and preserve existing triggers and grants. Standard Slack CLI deployment may update the app manifest/install state and affect monthly-report workflows as part of the bundle. No deployment, settings changes, new app/trigger/key or automatic rollback is authorized by this preparation. A manifest backup alone does not restore unknown old deployed source.

The staged proposal and durable/resume design are in deeplbot3x/stage1-preparation-ja.md. Pilot plus main is 390 trials; including the three smoke trials is 393, conservatively 39,300 submitted codepoints at 100 each. API-billed usage is separate. The 15-second start interval, twelve-session order and numeric stop thresholds require pilot validation and review, not automatic execution.
